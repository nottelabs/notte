# Generated endpoints for the Python SDK

Status: prototype (branch `v2-sdk-generated-endpoints`), 2026-10-13. Builds on
[openapi-contract.md](openapi-contract.md).

## Summary

The Python SDK's HTTP endpoint layer is generated from `openapi/openapi.json`; the models
are not. `scripts/generate_sdk_endpoints.py` turns each of the spec's 101 operations into a
factory in `notte_sdk/_generated/endpoints.py` that returns the operation's `NotteEndpoint`:

```python
def persona_emails_list(
    persona_id: str,
    *,
    params: wire.MessageReadRequest | None = None,
) -> NotteEndpoint[wire.EmailResponse]:
    """Persona Emails List (`GET /personas/{persona_id}/emails`).

    Responds with a JSON array: use `BaseClient.request_list`.
    """
    return NotteEndpoint(
        method="GET",
        path=f"/personas/{_segment(persona_id)}/emails",
        response=wire.EmailResponse,
        params=params,
    )
```

The hand-written clients keep their public methods and call the factories:

```python
from notte_sdk._generated import endpoints as api

def list_emails(self, persona_id: str, **data: Unpack[MessageReadRequestDict]) -> Sequence[EmailResponse]:
    """Reads recent emails sent to the persona [...]"""
    request = MessageReadRequest.model_validate(data)
    return self.request_list(api.persona_emails_list(persona_id, params=request))
```

This is the Python counterpart of the Node SDK's `sdk.gen.ts` (generated by
@hey-api/openapi-ts) wrapped by hand-written classes, minus the generated types: Python keeps
its models in `notte_core.types`, which the API itself renders into the spec.

## What is generated, what is hand-written

| Generated (`_generated/endpoints.py`) | Hand-written |
| --- | --- |
| One factory per operation, named after its `operationId` (leading `_` dropped) | Request/response models (`notte_core.types`, `notte_core.credentials.base`) |
| HTTP method, absolute path, path parameters (each encoded as one segment) | Ergonomic clients and resources (`PersonasClient`, `NottePersona`, ...), their signatures and docstrings, which the SDK reference is built from |
| Which model is the body, the response and the query parameters | Transport: retries, auth and preview headers, error mapping (`BaseClient`, `_transport.py`, `errors.py`) |
| Docstring: summary, response shape (object / array / page / file / none), unbound schemas, header parameters, query parameters the model does not cover | Streaming (function-run SSE), file upload/download, presigned storage URLs, websockets |

`BaseClient` changed in three small ways: a path starting with `/` is absolute (it does not
get the client's `base_endpoint_path`), errors name that path, and a POST/PATCH without a
request model sends no body (the spec has bodiless POSTs such as `function_fork`).

## Binding models by schema name

For each operation's body and response schema, the generator looks for, in order:

1. an override for this operation (`RESPONSE_MODELS`, `REQUEST_MODELS` in the script), used
   where the SDK parses a schema with a differently named model, e.g. `profile_delete`
   (`ProfileDeleteResponse`, same fields as `ExecutionResponse`) or `page_observe`
   (`Observation`, which the SDK exposes as `ObserveResponse`). The model's required fields
   must exist in the schema, or generation fails;
2. `openapi_contract.SCHEMA_NAMES` (imported, so the contract check and the generator agree
   on `SessionStartRequest` → `ApiSessionStartRequest` etc.);
3. the schema's namesake, after stripping FastAPI's `-Input` / `-Output` suffix.

A name binds if it is defined in `notte_core.types` / `notte_core.credentials.base` or
assigned there as an alias; plain imports in those modules do not count.
`PaginatedResponse_X_` binds to `X` (the client uses `request_list`).

Query parameters have no schema (FastAPI flattens them), so `QUERY_MODELS` maps an operation
to the model the SDK already sends (`persona_emails_list` → `MessageReadRequest`). The model's
fields must be query parameters of the operation and must cover the required ones; spec
parameters the model lacks are listed in the docstring (`only_current_token`, ...).

**Schemas without a model** (50 of 101 responses, 30 of 41 bodies): the factory is still
generated, with `body: BaseModel` and `NotteEndpoint[RawResponse]`. `RawResponse` is a
hand-written `extra="allow"` model, i.e. the JSON object, untyped. The docstring names the
missing schema. We chose this over skipping (the path and method of every operation stay
checked, the same way `files.py` already builds endpoints with a placeholder response) and
over generating TypedDicts (that is generating models, which the contract design rules out).
The rule for the ergonomic layer: **no public method returns `RawResponse`**; give the
schema a model in `notte_core.types` first, and the next generation binds it.

## Checks and refresh

| | |
| --- | --- |
| `make sdk-endpoints` | regenerate the module |
| `sdk-endpoints` pre-commit hook (`--check`) | the committed module is what the snapshot, the bindings and the models generate, and every `api.<operation>(` the SDK calls exists. Offline. Runs on changes to the snapshot, the SDK, `notte_core.types` and the scripts |
| `bump-openapi` workflow | after fetching the staging spec, regenerates the module and commits it with the snapshot, so an endpoint change is a reviewable diff. A spec the bindings no longer fit leaves the module stale: the PR's hook fails and the generator's error is in the PR body |
| `make openapi-check-prod` (release gate) | also runs `--check --against https://api.notte.cc`: every operation the SDK calls must generate identically from the production spec (same method, path, parameters, models). Operations the SDK does not call cannot block a release |
| `--report` | lists generated operations as used / unused, and calls with no operation |

Output is deterministic: operations are sorted by tag, path and method; the code is emitted
already in the repo's ruff format (magic trailing commas), and the header carries the spec
version.

## Approach and alternatives

| | In-repo generator (chosen) | openapi-python-client + custom templates | datamodel-code-generator / openapi-generator |
| --- | --- | --- | --- |
| Runtime dependency | none (reuses `NotteEndpoint` / `BaseClient` on requests) | generated client uses httpx + attrs; templates must be rewritten to bind pydantic models from `notte_core` | models only (the opposite of what we need) / JVM toolchain |
| Model constraint | binds by schema name, never emits models | must suppress its model generation and rewrite every reference | generates models |
| Determinism, basedpyright strict | yes (checked in CI) | output needs post-processing to pass strict mode | n/a |
| Retries, auth headers, error mapping, version hints | inherited from `BaseClient` | reimplemented in templates or a wrapper | n/a |
| Cost | ~500 lines of script, one file to read | template fork to maintain across upgrades | n/a |

## Migration plan

Small PRs, each keeping public signatures and docstrings (the docs hook proves it: the SDK
reference must not change) and pinning the wire with a request-capturing test like
`tests/sdk/test_generated_endpoints.py`:

1. **This PR.** Generator, checks, refresh and release gate; `profiles.py`, `personas.py`,
   `vaults.py` migrated (1255 → 945 lines; the only hand-written endpoints left there are
   the two off-spec phone-number routes).
2. **Contract for overrides**, after #22: move `RESPONSE_MODELS` / `REQUEST_MODELS` into
   `openapi_contract.py` so overridden models are drift-checked too.
3. **`files.py`**: multipart upload via `api.upload_session_file(...).with_file`, list,
   download (`request_path` on the generated endpoint), delete. Add a `SessionFileListRequest`
   model for `limit` / `offset` / `source`.
4. **`sessions.py` CRUD and `page.py`**: start/stop/status/list/cookies/debug/replay/offset/
   auth, observe/scrape/execute (`page_execute` query parameters get a model).
5. **`functions.py` metadata**: create/update (multipart), get/delete/list/fork, run
   get/update/stop/list, payload upload. Needs a decision on `list_functions` (bind the whole
   page to `ListFunctionsResponse`, or add `FunctionListItemResponse`), and drops the
   `?restricted=` path string.
6. **Function-run streaming**: settle `runs/{run_id}` vs `runs/start` with the backend, then
   build the SSE loop on the generated endpoint's `request_path`.
7. **Off-spec routes**: the API publishes the 9 hidden routes (or we drop them); migrate
   `managed_auth.py` and the rest; then remove `base_endpoint_path` and relative paths.
8. **Parity with Node**: for each missing operation, add its models to `notte_core.types`,
   then the public method.

## Risks

- **Public API.** Methods, signatures, return types and docstrings are unchanged, and the
  generated SDK reference does not change. Removed: private `_*_endpoint` helpers and the
  class-level path fragments (`PersonasClient.LIST_EMAILS`, `VaultsClient.CREATE_VAULT`, ...),
  which were relative to the client's base path and not documented.
- **Wire changes.** List calls lose the trailing slash (now exactly the spec path), and path
  parameters are percent-encoded as one segment (an id containing `/` used to address another
  route).
- **Operation renames.** Factories are named after `operationId`s, so a backend rename renames
  a factory. `--check` fails the refresh PR when the SDK calls a name that disappeared;
  pinning operation ids in the backend avoids the churn.
- **Staging ahead of production.** The refresh PR follows staging; the release gate blocks a
  release whose called operations production serves differently.
- **Operations without models.** `RawResponse` must stay internal (rule above).
- **Streaming and files.** `request` / `request_list` parse JSON; binary, no-content and SSE
  responses keep hand-written transport code, built on the generated path and method.
- **Async.** The SDK is sync (`requests`). The factories are plain data, so an async
  `BaseClient` could reuse them unchanged.
- **Size.** The generated module is ~1,600 lines; it is reviewed as a diff in refresh PRs, not
  read.
