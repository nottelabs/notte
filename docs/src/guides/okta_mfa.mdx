An agent can complete an Okta sign-in end to end, including the MFA step, when the second factor is a
TOTP authenticator. You store the TOTP secret in a [Vault](/concepts/vaults) and Notte generates the
one-time code at the moment the challenge appears.

<Note>
  Okta Verify push cannot be automated. Approval happens on an enrolled physical device, and the
  enrollment QR carries a one-time activation token rather than a shared secret. Use a TOTP
  authenticator instead, as described below.
</Note>

## Prerequisites

- Admin access to your Okta org
- The [Notte CLI](/integrations/claude-code-ai-agents) installed and authenticated with `notte auth login`
- A coding assistant such as Claude Code, with the Notte skill installed via `notte skill add`

Use a dedicated service account rather than a person's identity. A TOTP secret is equivalent to the
factor itself, so anyone holding it can pass the challenge. Grant the account only the app access the
automation needs.

## Set up the Okta side

<Steps>
  <Step title="Create a service account">
    In the Okta Admin Console, go to **Directory** then **People** and add a user for the automation,
    for example `agent-svc@yourcompany.com`.
  </Step>

  <Step title="Enable Google Authenticator">
    Go to **Security** then **Authenticators**, click **Add authenticator**, and add Google
    Authenticator. It registers as a possession factor.

    ![Okta Authenticators page with the Add authenticator button marked and Google Authenticator listed as active](/images/okta-mfa/authenticators.png)

    On the **Enrollment** tab, set Google Authenticator to Optional or Required for the group your
    service account belongs to.

    <Warning>
      Check **Security** then **Authentication Policies** too. If the rule protecting your app
      requires a phishing-resistant or device-bound factor, Okta rejects TOTP and keeps asking for
      Okta Verify. The rule has to accept any possession factor. This is the step most likely to
      block you.
    </Warning>
  </Step>

  <Step title="Enroll and reveal the secret">
    Sign in as the service account, open its end-user settings, and set up Google Authenticator. On
    the QR screen, click **Can't scan?** to reveal the base32 secret.

    ![Okta Google Authenticator enrollment screen with the Can't scan link marked](/images/okta-mfa/reveal-secret.png)

    Copy that value. It is the `mfa-secret` in the next step.

    <Tip>
      Okta Verify shows a QR too, but it encodes an `oktaverify://` activation URL with no secret in
      it. Only a TOTP authenticator gives you a reusable seed.
    </Tip>
  </Step>
</Steps>

## Set up the Notte side

<Steps>
  <Step title="Store the credentials in a Vault">
    Create a vault and add the Okta credentials. Keep the `vault_id` it returns.

    ```bash
    notte vaults create

    notte vaults credentials add \
      --vault-id <vault-id> \
      --url "https://<your-org>.okta.com" \
      --email "agent-svc@yourcompany.com" \
      --password "<password>" \
      --mfa-secret "<base32-secret>"
    ```

    Credentials are encrypted at rest and never reach the model. Notte substitutes the real values
    into the page only at fill time, and generates the one-time code from the stored secret.
  </Step>

  <Step title="Start a session">
    Create a profile so the signed-in state can be saved, then start a session with both attached.

    ```bash
    notte profiles create

    notte sessions start -y \
      --vault-id <vault-id> \
      --profile-id <profile-id> \
      --profile-persist
    ```

    <Warning>
      Pass `-y`. Without it the CLI can stop on a confirmation prompt when another session is already
      running, and in a non-interactive shell the session still starts but your flags are dropped,
      leaving you with no vault and no profile.
    </Warning>
  </Step>

  <Step title="Let your coding assistant drive the sign-in">
    With the Notte CLI and skill installed, ask Claude Code to walk the flow in plain language:

    ```text
    Using the notte CLI on session <session-id>, sign in to https://<your-org>.okta.com.
    The credentials are in the attached vault. If Okta offers a choice of security method,
    choose Google Authenticator, not Okta Verify. Observe the page after each step and stop
    when the Okta dashboard has loaded.
    ```

    It drives the browser with `notte page goto`, `notte page observe`, `notte page click` and
    `notte page fill`, checking the page between actions. See
    [Claude Code & AI Agents](/integrations/claude-code-ai-agents) for the full loop.
  </Step>

  <Step title="Confirm it worked">
    ```bash
    notte page observe --session-id <session-id>
    ```

    A successful sign-in lands on `/app/UserHome`. You can also download the recording with
    `notte sessions replay --session-id <session-id>`.
  </Step>
</Steps>

## Result

The agent fills the username, picks Google Authenticator from the security method list, enters a code
generated from the stored secret, submits the password, and lands on the dashboard. No device and no
person in the loop.

Because the assistant reads the page before each action, it follows whatever order your org uses. The
run above asks for the factor before the password, which is an Okta policy choice rather than a fixed
sequence, and a hardcoded script would break on it.

## Reuse the signed-in state

With `--profile-persist`, the browser state is written back when the session closes, so the Okta
domain carries its cookies into the next session that attaches the same profile. See
[Browser Profiles](/features/sessions/browser-profiles) for how to reuse and refresh that state.
