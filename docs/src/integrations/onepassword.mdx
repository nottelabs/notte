There are two ways to use 1Password with Notte:

| Method | Who approves | Where the values go |
|---|---|---|
| [Agentic Autofill](#agentic-autofill) | A person, per login, in the 1Password app | 1Password fills the form in the Notte browser. Your code, your agent and Notte never see the values |
| [1Password SDK](#1password-sdk-with-a-service-account) | Nobody, a service account reads the vault | Your code reads the values and types them into the page |

## Agentic Autofill

With [1Password Agentic Autofill](https://developer.1password.com/docs/agentic-autofill/), your agent asks for access to a login, a person approves it in 1Password, and the 1Password browser extension fills and submits the login form in the Notte session. Notte keeps only opaque references to the approved logins.

<Note>
Agentic Autofill is in partner preview. Its routes are not in the API reference or the Notte SDKs yet, so the examples below call the HTTP API directly.
</Note>

### Before you start

- A 1Password Business account whose administrator allows AI agents to autofill. See [1Password for agents security](https://support.1password.com/1password-for-agents-security/).
- Connect 1Password in the [Notte console](https://console.notte.cc): **Settings > Integrations > 1Password > Connect**, then sign in to 1Password. The connection belongs to you, not to your workspace.
- A Notte API key of yours, set as `NOTTE_API_KEY`. The routes use the 1Password connection of the person who owns the key.

### How it works

1. Start a session with `"onepassword": true`. It starts in the `authenticating` state: CDP, page actions and live viewers are refused until you release it.
2. Create an access request for up to 5 websites. The response holds an `app_link`. Send it to the person, who opens it on the device where 1Password runs. Never put it in a model's context.
3. Poll the access request until it is no longer `pending`. Once `resolved`, it lists one grant per approved login.
4. Call `fill` with a grant and the login page URL. The extension fills the username and password and submits the form. For a login that spans several pages, call `fill` on each page.
5. Release the session. Fills stop, every page reloads, and the session opens to your code, CDP and viewers like any other session.

### Routes

All routes take your API key as a bearer token.

| Route | Body | Returns |
|---|---|---|
| `POST /sessions/start` | `{"onepassword": true}` plus other session options | The session, including `session_id` |
| `POST /sessions/{session_id}/onepassword/access-requests` | `entries` (1 to 5) and an optional `goal` (up to 140 characters) | `id`, `state` and `app_link` |
| `GET /sessions/{session_id}/onepassword/access-requests/{request_id}` | | `id`, `state` and, once `resolved`, `grants` |
| `POST /sessions/{session_id}/onepassword/fill` | `grant_id` and an optional `url` | `status` and `url` |
| `POST /sessions/{session_id}/onepassword/release` | | `204 No Content` |

Each entry of an access request takes:

- `website`: the site's HTTPS URL. A bare host such as `github.com` is read as `https://github.com`.
- `reason` (optional): up to 100 characters, sent to 1Password with the request.
- `keywords` (optional): up to 5 words of up to 50 characters each, sent to 1Password with the request.

**Polling.** Notte checks with 1Password on a schedule, about every 2 seconds at first and then less often, down to once a minute for requests older than 3 minutes. Reading the request more often returns the last known state, so polling every few seconds is enough. Any state other than `pending` is final, and only `resolved` returns grants. A grant has an `id`, its `website` and `granted_at`.

**Filling.** With `url`, the session opens that page first; without it, the fill runs on the current page. The page must be on the grant's website, or the fill fails with `origin_mismatch`. `status` is 1Password's result: `fill_submitted` means the form was submitted, not that the site accepted the login. Check the returned `url` (without its query string or fragment) to see where the site sent you, then call `fill` again if it shows another login step.

**Releasing.** If a fill is still running, release answers `409` with `onepassword_fill_in_progress`; call it again. After release, `fill` is refused with `onepassword_session_released`. To sign in again, start a new session.

### Reusing grants

A grant stays valid for 30 days. Save its `id`, and in a later session started with `"onepassword": true`, call `fill` with it directly, without a new access request. If `fill` answers `onepassword_grant_invalid`, create a new access request.

### Why the session is locked until release

While 1Password fills a form, the username and password are in the page until the form is submitted. Any script attached to the browser over CDP could read them. So a session with `onepassword: true` runs no customer code at all until you release it: no CDP, no page actions, no viewers. Release reloads every page, since a form submitted by script can keep the password in the page, and the browser refuses fills from then on. Request bodies are left out of the session's network logs before a fill, and session replay is off for these sessions.

After release, your code gets the signed-in browser, including its cookies. The integration protects the password, not the login session it produces.

### Limits

A session with `onepassword: true` cannot also use:

- a [secret proxy](/integrations/secret-proxy), whose certificate authority could read the login request
- Demonstrate (`demonstrate`)
- `auth_ids`
- an external `cdp_url`
- the routes that create a session and connect to it in one call

If your 1Password connection expires or is revoked, the routes answer `onepassword_needs_reauth`. Connect 1Password again under **Settings > Integrations**.

## 1Password SDK with a service account

Use the [1Password SDK](https://www.1password.dev/sdks) to read login fields and fill them in a Notte browser. The values pass through your code. The Python and TypeScript examples submit a test form without printing the field values.

### Set up

Create a [1Password service account](https://start.1password.com/developer-tools/infrastructure-secrets/serviceaccount/) with read access to a test vault containing a dummy Login item. Set `OP_SERVICE_ACCOUNT_TOKEN`, `OP_USERNAME_REF`, and `OP_PASSWORD_REF`. Field references use `op://vault/item/field`; see [1Password's reference syntax](https://www.1password.dev/sdks/load-secrets).

Set `NOTTE_API_KEY` from [Notte](https://console.notte.cc/apikeys), then clone the [Notte repository](https://github.com/nottelabs/notte) and open [examples/onepassword](https://github.com/nottelabs/notte/tree/main/examples/onepassword). Its README includes the installation commands.

<Tabs>

  <Tab title="TypeScript">

### Use your login page

The example fills and submits an in-memory test form. Reuse its `fill_login` or `fillLogin` helper on your page and adapt the labeled field and button locators. It resolves only the two supplied references.

Each attempt owns its Notte browser and closes it after success or failure. The result includes the session ID and submission status.
